## 三、维度 1·效率 / 质量改善（权重 50%）

### 选用评分标准

按活动 §4.1 维度1 的三类标准：
- **标准 1（效率可量化）**：部分适用——单次任务提效有数据支撑
- **标准 2（质量可量化）**：部分适用——复用判断准确率、规范覆盖率有改善
- **标准 3（难量化，评委判断）**：主要标准——核心价值是"改变工作方式"，难纯数字衡量

下面同时给出三类标准的论据。

### 3.1 量化提效估算（标准 1）

⚠️ 当前 toolkit 刚发布，量化数据基于设计阶段的对照估算 + 部分自身使用观察，未经多人多场景验证。

| 任务 | 之前（裸 AI 协作）| 之后（用 toolkit）| 提效估算 |
|---|---|---|---|
| 接到 PRD → 输出需求摘要 + 风险 + 落点 | 手动喂项目背景 ~10 min + AI 给方案 ~5 min ≈ **15 min** | `/toolkit 需求 <PRD>` 自动读项目地图 + 输出结构化结论 ≈ **3 min** | **80%** |
| 复用判断（"这个组件有没有现成的？"）| AI 凭印象答 → 人工 grep 验证 ~5 min/次 | 强制三步搜（速查表 → ls → grep），AI 直出 file:line ≈ **1 min** | **80%** |
| 接口联调 mock 数据 | 手动按字段表造 5 种态 ~20 min | `/toolkit 接口 <Apifox 链接>` 自动生成五态 mock ≈ **3 min** | **85%** |
| 提交前自查 | 全靠人工 review ~15 min | `/toolkit review` 三段式预审 + 人工只看阻塞项 ≈ **5 min** | **66%** |

**单次需求综合提效估算**：原 ~60 min → 现 ~15 min，**提效比 ≈ 75%**（对应活动 §4.1 标准 1 的 70-100 档）。

### 3.2 量化质量估算（标准 2）

| 维度 | 之前 | 之后 |
|---|---|---|
| AI 给的"复用建议"准确率 | 主观 ~60%（常凭印象编造）| 强制三步搜 + 必须 file:line，**接近 100% 不编造** |
| 项目规范覆盖率（接口/样式/反模式）| 0%（每次新对话重讲）| 100%（项目知识层 `.claude/toolkit/` 持久化）|
| 跨项目方案的迁移成本 | 高（每个项目重教 AI）| 低（通用工作流 + 项目特定地图分层）|

## 五、维度 3·风险控制与边界清晰度（权重 20%）

按活动 §4.1 的 4 项关键风险点逐条覆盖：

### 5.1 ✅ AI 产出的验证方式（如何判断对错？）

- skill 在每个阶段都有强制人工确认点，特别是阶段一明确要求"接口字段、错误码、鉴权、边界状态、业务规则**必须显式列出'待人工校验'**"
- 阶段五 review 输出三段式：阻塞项 / 建议项 / 未发现项——"未发现项明确说'未发现 X 类问题'，不要凑"
- 复用建议**必须给具体 file:line**，找不到时强制说"无可复用项，不准硬凑"
- skill 硬性约束："找不到信息时承认找不到，不编造路径、组件名、接口字段"

### 5.2 ✅ 数据安全 / 脱敏处理

- skill 工作流不引入额外的数据流转——所有读写仍在用户本地 Claude Code 会话内
- skill 配套的输入读取策略章节明确**禁止账号密码贴 CC 对话框**（使用 playwright 时强制走可见浏览器登录窗口）
- 项目知识层 `.claude/toolkit/` 是 **per-repo 文件**，由各项目自行控制是否提交到 git，敏感项目可 `.gitignore` 排除
- 公开 SKILL.md 内容不含任何项目敏感信息（仅工作流规则），项目特定信息（接口、字段、业务规则）由各项目自行管理在私有仓库

### 5.3 ✅ 不适用场景（边界声明）

skill 自身的"何时不使用"章节明确：
- 纯 git 操作、纯 CI/CD 配置、纯运维问题、与代码无关的咨询

本案例的不适用场景：
- 没有相对稳定流程的探索性 / 一次性项目
- 单 prompt 能完成的小任务（用 toolkit 反而是过度设计）
- 不愿维护项目知识层的团队（地图过期会让 skill 失效）
- 非 Claude Code 宿主（虽然 npx skills 已兼容多家 agent，但深度功能仅 Claude Code 适配）

### 5.4 ✅ 人工复核节点（哪一步由谁把关？）

明确的人工把关节点：

| 阶段 | 人工把关内容 | 由谁把关 |
|---|---|---|
| 阶段一 | 需求归类（新功能 vs 优化）、改动落点确认 | 申请人 / 项目负责人 |
| 阶段三 | 接口字段、错误码、鉴权、边界场景 | 申请人 + 接口提供方 |
| 阶段四 | 实现是否符合子模块约定 | 申请人 |
| 阶段五 | review 输出仅是预审，不替代人工最终 review | 申请人 + 同行 reviewer |
| 阶段六 | 地图维护走"改动提案 → 用户确认 / 调整 / 取消"格式，AI 不私自改规范 | 申请人 |

skill 硬性约束："AI review 是预检，不替代人工 review、测试和业务验收。"

**4 项全覆盖 + 完整复核流程** → 对应活动 §4.1 维度 3 的 **90-100** 档。

## 七、AI 应用背景与具体实践（精简版）

### 7.1 痛点（为什么做）

AI 应用部前端日常处理高度结构化的需求——几乎每个需求都走"PRD 拆解 → 方案设计 → 接口联调 → 页面实现 → 提交前 review"链路。但裸 AI 协作有 4 个反复痛点：

1. 每次都要重新喂项目结构（mai/aise/aiagent 等子模块边界不同）
2. AI 复用建议靠拍脑袋，常编造组件名
3. 提交前缺结构化预审，明显问题留到人工 review 才发现
4. 经验沉淀靠脑内，下次新对话又得重讲

### 7.2 解决方案（做了什么）

```
┌───────────────────────────────────────────────────────────────┐
│   /toolkit 需求 ──→ 方案 ──→ 接口 ──→ 实现 ──→ review ──→ 维护    │
│      ①         ②       ③       ④        ⑤        ⑥        │
│   理解需求    设计      联调     落码      自查     沉淀地图       │
│      │                                              ↑         │
│      └──────────── 项目知识反哺 PROJECT-MAP ─────────┘          │
└───────────────────────────────────────────────────────────────┘
```

**知识分层架构**：

```
~/.claude/skills/toolkit/SKILL.md       ← 通用工作流（user-scope，跨项目复用）
<项目根>/.claude/toolkit/                ← 项目特定知识层（每个项目自管理）
├── PROJECT-MAP.md                       ← 子应用/模块概览索引
├── sub-apps/<name>.md                   ← 子应用深度地图
├── review-standards.md                  ← 项目特定评审标准
└── examples.md                          ← 阶段示例
```

**横切机制**：复用查找规则（强制 file:line）/ 差异处理（显式标注 + 询问存档）/ 提案式地图维护 / MCP 输入决策树。

### 7.3 元案例：AI 设计 AI 自己用的工作流

skill 的设计、目录结构、README、GitHub 发布、npx 集成、文档拆分提案——全程跟 Claude 协作完成。整个过程对话历史可作为"AI 真的能干活"的演示素材。
