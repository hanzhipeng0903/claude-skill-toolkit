# claude-skill-toolkit 案例说明

> 一份给 Claude Code 用的 skill，把 AI 应用部前端日常的"PRD → 实现 → review"全链路做成结构化工作流。
> 公开仓库：<https://github.com/hanzhipeng0903/claude-skill-toolkit>

---

## 速览：亮点 + 实战印证

### 设计亮点（skill 本身的工程化设计）

1. **知识分层（§4.1）** ——通用工作流跟 user 走、项目特定规范跟项目走（`<项目根>/.claude/toolkit/`），**换项目零迁移**
2. **复用查找规则强制 file:line（§4.2）** ——三步搜（速查表 → ls → grep），找不到就承认，从源头堵掉 AI"编造组件名"的失误模式
3. **差异显式标注 + 主动询问存档（§4.3）** ——AI 推断被纠正 / review 发现反复出现的问题时主动询问"是否沉淀进地图"，让维护契机被工作流本身自动暴露
4. **提案式地图维护（§4.4）** ——AI 改项目规范必须走"应用前 / 应用后 / 关联建议 → 用户确认"格式，**不私自改**
5. **MCP 输入策略决策树（§4.5）** ——读登录态走 playwright、调试走 chrome-devtools、公开静态走 WebFetch，**工具中立 + 失败时按规则降级**
6. **路径推荐（§三末）** ——阶段一根据复杂度自动推 4 条链路（完整 / 精简 / 极简 / 仅 review），用户回 `继续` 自动衔接，做小事不啰嗦、做大事不漏环节
7. **工程化分发（§五）** ——npx 一行装、cross-platform、兼容 Claude Code / Cursor / Codex / OpenCode
8. **MCP 工具复用：分析延伸到回归（§4.5 + §6.7）** ——同一份输入策略决策树既驱动 PRD 抓取（playwright），又驱动改动后的自动化回归（chrome-devtools 抓 XHR / 监控制台 / 跑 Lighthouse），让 skill 成为"PRD → 实现 → 验证"完整链路的骨架
9. **跨工种可复用：核心机制不绑定前端（§4.3 / §4.5 / 阶段六）** ——三大核心能力（**需求结构化拆解 / MCP 输入策略决策树 / 提案式经验沉淀**）都是工作流形状无关的：换成后端 API 设计、移动端开发、测试用例规划、研究报告分析、产品方案评审，都能**直接套用**，只需替换项目知识层（PROJECT-MAP + 深度地图）的填充内容。skill 提供的不是某个领域的工作流脚本，而是"**如何把任意工程化工作流跟 AI 协作工程化**"的范式

### 实战印证（§六，mai-static · 4 条 P1 PRD 需求）

1. **反模式条目预先命中** ——深度地图 §10.2 记录的 `productList` 跨页勾选 bug 直接命中需求 10，**L24 / L72 / L120-123 行号一字不差**。"经验脱离脑内、序列化到地图、跨对话被 AI 直接利用" 第一次有了实证
2. **27+ 处 file:line 全部经 grep/Read 验证、零编造** ——复用查找规则把 AI"自信地胡说"从源头堵死
3. **输入策略降级实操跑通** ——chrome-devtools 抓不到 Canvas 表格 + 虚拟滚动 → 切 playwright → 排查 lockfile → 清理 7 个残留 Chromium → 步进抓取拿到全部 10 条需求。SKILL 提前警告的"chrome-devtools 不擅长长文档"**被实证**
4. **差异处理把灰色地带摆上台面** ——需求 1 grep 命中 3 处 `docs.qq.com` 链接，AI 主动列出"哪条在范围、哪条不在"，提示 PRD 作者确认是否一并修；**不替用户拍板**
5. **副产物自然产生** ——实战中自然冒出 3 条可沉淀回地图的内容（视频生成设置项映射 / playwright 锁诊断步骤 / PRD 提取范式），**现场演示阶段六维护机制的设计意图**
6. **提效 ~80%** ——4 条 P1 阶段一分析 2-4 h → 30 min，与设计估算 75% 基本吻合

## 一、为什么会做这件事

AI 应用部前端的日常工作高度结构化——几乎每个需求都走同一条链路：拿到 PRD、拆解需求、做方案、对接接口、写页面、提交前 review。这条链路足够稳定，按理说"用 AI 协作"应该能很顺。但实际跟 Claude / Cursor 协作时，会反复撞到几个本质问题：

**第一，每次新对话都要重新喂一遍项目背景。** mai、aise、aiagent 等几个前端项目的子模块边界、组件规范、API 范式都不一样。AI 不知道这些就只能给泛化建议——而泛化建议落到具体项目里要么用不上、要么得大改。每次解释项目结构光提示词就得花 5-10 分钟。

**第二，AI 的"复用建议"普遍不可信。** "建议复用已有组件"是一句出现频率极高的回答，但十次里有六七次：要么编造一个不存在的组件名，要么真有但方位描述模糊。最后还是要人工 grep 验证一遍才敢用——AI 反而成了**多一道核对工序**。

**第三，提交前的预审环节是空白。** 写完代码到提测之间没有结构化的自查节点，命名错位、边界遗漏、规范偏离这些低级问题留到人工 review 才发现，浪费两边的时间。

**第四，经验只能存在脑子里。** 上次踩过的坑、定过的口径、AI 给错过的判断纠正——下次开新对话又得重讲。AI 协作过程中产生的判别信号没有可持久化的位置。

这四件事的共同本质是：**AI 协作本身没有被工程化。** 不是缺工具，而是缺把"如何用 AI 做交付"这件事当作工作流来设计的视角。

## 二、设计思路

围绕上面四个问题，定下三条原则：

**1. 工作流要稳定可复现，不是"想到什么聊什么"。**
把 6 阶段（需求理解 / 方案设计 / 接口联调 / 页面实现 / 提交前 review / 地图维护）作为一等公民——每个阶段有明确入口、固定输出形态、阶段间显式衔接。这样任何一次需求都能踏在同一个流程上推进，不会每次重新发明。

**2. 知识必须分层，跟人走的归人，跟项目走的归项目。**
通用规则（怎么拆 PRD、怎么做 review）放 user-scope 的 skill；项目特定规范（mai 的子模块边界、aise 的接口风格）放各项目根的 `.claude/toolkit/`。这两层独立维护——换项目不用换 skill，skill 升级也不影响项目。

**3. AI 的失误模式要在 prompt 层就被约束。**
不是"AI 表现好"靠运气，而是把已知会出错的地方变成硬约束：
- 复用建议必须给 file:line，找不到就直说"无可复用项"，**不准硬凑**
- 接口字段、错误码、鉴权、边界状态**必须显式标注"待人工校验"**
- 地图过期与代码冲突时**显式指出**而非默默处理
- AI 不私自改项目规范，所有维护操作走"改动提案 → 用户确认"流程

这几条本来是 prompt engineering 经验，把它们刻进 skill 文件，就变成跨场景的护栏。

## 三、6 阶段工作流：长什么样

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   /toolkit 需求 ──→ 方案 ──→ 接口 ──→ 实现 ──→ review ──→ 维护   │
│      ①         ②       ③       ④        ⑤        ⑥       │
│   理解需求    设计      联调     落码      自查     沉淀地图      │
│      │                                              ↑        │
│      └──────────── 项目知识反哺 PROJECT-MAP ─────────┘         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

每个阶段都是一条 `/toolkit <关键词>` 命令：

- **阶段一·需求理解**：先判断是【新功能】还是【原有功能优化】（这两类的处理方式差很多），自动读项目地图判断需求归属，输出需求摘要 + 改动落点 + 复用建议（带 file:line）+ 风险点。
- **阶段二·方案设计**：模块拆分、组件复用、状态管理、路由接入、mock 策略——所有建议都必须命中现有项目模式，不引入新框架。
- **阶段三·接口联调**：吃 OpenAPI / Apifox 链接，吐 TypeScript 类型 + 五种态的 mock（正常 / 空 / 异常 / 权限不足 / 分页边界）+ 请求封装。
- **阶段四·页面实现**：按子模块的代码风格写代码，禁 inline style，强制走深度地图记录的项目约定。
- **阶段五·提交前 review**：阻塞 / 建议 / 未发现 三段式输出，"未发现"明确说"未发现 X 类问题"，不允许凑数。
- **阶段六·地图维护**：把这次需求里发现的新规则、新反模式、新速查项沉淀到项目地图——走"应用前 / 应用后 / 关联建议"的提案格式，等用户 `确认 / 调整 / 取消`。

最有意思的是阶段一末尾的**路径推荐**——根据需求复杂度自动推荐 4 条链路：

- **完整**：① → ② → ③ → ④ → ⑤（新功能 / 大重构）
- **精简**：① → ③ → ④ → ⑤（仅接口对接）
- **极简**：① → ④ → ⑤（UI 微调 / bug 修复）
- **仅 Review**：① → ⑤（只想看分析不动代码）

用户回 `继续` 即按推荐路径自动衔接，不用每次重打 `/toolkit`。这一条让"做小事不啰嗦、做大事不漏环节"同时成立。

## 四、几个关键设计

### 4.1 知识分层

```
~/.claude/skills/toolkit/SKILL.md       ← 通用工作流（user-scope）
<项目根>/.claude/toolkit/                ← 项目特定知识层
├── PROJECT-MAP.md                       ← 子应用/模块概览索引
├── sub-apps/<name>.md                   ← 子应用深度地图（架构 / 组件规范 / API 范式 / 反模式 / 速查表）
├── review-standards.md                  ← 项目特定评审标准
└── examples.md                          ← 阶段示例
```

这个分层是整个 skill 真正"跨项目可用"的关键。skill 进入任一阶段前会先读对应项目的深度地图——读完后大多数任务**无需再扫源码**，直接在地图上推理。地图就是把"项目老人脑子里的东西"序列化出来给 AI。

### 4.2 复用查找规则

任何"建议复用 X" 都强制走三步：

1. 看深度地图速查表（"找 X 去哪"那一节）
2. ls 子模块对应目录
3. grep 关键词

**找到必须给 file:line**，三步都没找到就输出"无可复用项，建议新建"，**不许凑**。

这条规则的价值不在于步骤本身，而在于把 AI 编造组件名的失误模式从源头上堵掉。

### 4.3 差异处理：明摆着比偷偷处理强

skill 工作中遇到任何"差异"都强制**显式标注**：地图说 A 代码是 B、用户描述位置找不到、用户疑似新功能但地图已有类似——所有这些都摆到对话台面上，让用户决定怎么处理，不让 AI 替用户拍板。

更进一步，遇到两类差异 AI 会主动询问"是否沉淀进地图"：（a）AI 推断被用户纠正时，（b）review 发现某个项目特定问题反复出现时。这就是阶段六维护机制的天然触发器——不靠人主动想着维护，靠工作流本身把维护契机暴露出来。

### 4.4 提案式地图维护

阶段六改地图必须走固定提案格式：

```
## 改动提案
- 目标文件 / 目标位置 / 规范类型 / 操作类型 / 理由

### 应用前    （现状片段）
### 应用后    （改后片段）
### 关联建议  （可能要同步的位置）

回复 `确认` 应用 / `调整：<新描述>` 重做 / `取消` 终止
```

AI 不私自改项目规范——这条规则保证了 skill 维护项目知识时不会失控。

### 4.5 输入策略决策树

读不同类型的输入走不同 MCP，写进 skill 作为通用决策表：

| 想做的事 | 用哪个 MCP |
|---|---|
| 读登录态文档（飞书 / Notion / 内网 wiki / 私有 Apifox）| playwright-bg → playwright → browsermcp 链路 |
| 读公开静态页 | WebFetch |
| 抓 XHR / 看控制台 / 跑 Lighthouse / 性能 trace | chrome-devtools |
| 操作页面（点击 / 填表 / 上传）| playwright |
| 截图 | 不接受，要求文字化 |

工具中立——用户机器有什么 MCP 就用什么，不绑死单一栈。skill 还硬性禁止把账号密码贴到 CC 对话框，登录走可见浏览器窗口让用户自己输。

## 五、工程化分发

skill 不只是放本地用——已经做了完整的对外发布：

- 公开 GitHub 仓库（MIT 协议）
- **一行命令安装**：`npx skills add hanzhipeng0903/claude-skill-toolkit -g -y -a claude-code`
- cross-platform，无需 root，依赖只 Node ≥ 18
- 兼容 `npx skills`（Vercel Labs 主流社区安装器），同一份 SKILL.md 也能装到 Cursor / Codex / OpenCode
- 备用 curl 单文件下载（不愿装 Node 的退化方案）
- 配套 `CLAUDE.md` 约束 Claude 改 SKILL.md 时的硬规则、`README.md`、`LICENSE`、`share.md` 群内分享文案

**装好就能用**——这是分发设计上比较关键的一点。很多团队 AI 实践停留在"在私有文档里写个 prompt"，从"我用着好"到"别人也能用上"中间有个很厚的台阶。这次把这个台阶用工程化方式抹平了。

## 六、实战：在 mai-static 真实 PRD 上跑了一次

设计完工作流不算实践——让它在一个真实任务上跑出可信结果，才能验证。

### 6.1 任务

- **项目**：焦点科技 mai-static（多子应用前端代码仓，含 mai/assistant、mai/astronaut、mai/aip 等）
- **来源**：飞书 PRD「基于新人体验报告的优化prd 4/29」（10 条需求，登录态文档）
- **任务**：从 10 条需求里筛 4 条 P1 纯前端需求 → 分析每条的所属子模块、改动落点（具体到 file:line）、改动量、影响范围
- **项目知识层状态**：mai-static 已有完整的 `.claude/toolkit/`（PROJECT-MAP + mai-assistant 深度地图 + mai-astronaut 深度地图 + review-standards + examples）

只跑了**阶段一·需求理解**，但过程中触发了 skill 几乎所有横切机制：输入读取策略决策树、项目知识层加载与子模块归属判断、复用查找规则、差异处理、反模式条目命中。

### 6.2 关键时刻：反模式条目预先命中（最强证据）

需求 10 是"社媒营销跨页勾选丢失"——用户在第 1 页勾 2 个 + 第 5 页勾 2 个，提交时只剩第 5 页的 2 个。

阶段一读到这条 PRD 后，**直接命中**深度地图 §10.2 反模式条目：

> components/productList/ — 跨页勾选状态丢失 bug（selectedProdIds 是局部 useState；submit 时只过滤当前页 elements，跨页选中 ID 丢弃）。详见 [products/productList/index.jsx:24, 56-66, 72, 120-123]

读源码验证，**行号一字不差**——L24 / L72 / L120-123 全部对得上。

这条记录是上次有人踩过、被显式沉淀进地图的"项目特定坑"。这次新需求来时 AI 不再"重新发现 bug"，而是**直接定位到已记录的根因 + 准确行号 + 影响面警告**（地图原文："改这个公共组件要全仓 grep 调用方"——后续 grep 也证实有 2 处调用方需要回归测试）。

**这是地图驱动工作流最强的证据：经验真的可以脱离脑内、被序列化到地图、然后跨对话被 AI 直接利用。**

![子模块归属与反模式命中](./screenshots/06-子模块归属与反模式命中.png)

> 阶段一一次输出对 4 条 P1 需求的子模块归属（依据 PROJECT-MAP + 深度地图）。
> 表格第 4 行直接命中深度地图 §10.2 反模式预先记录的 `components/productList/` 跨页勾选 bug，行号 24 / 56-66 / 72 / 120-123 一字不差对照——这就是"经验序列化进地图、跨对话被 AI 直接利用"的实证。

### 6.3 工具失败 → 优雅降级（输入策略实战）

PRD 是飞书登录态文档。SKILL 输入策略：playwright-bg → playwright → browsermcp → 让用户贴正文。实际过程：

1. 用户先指定 chrome-devtools → 抓到部分内容但 **Canvas 渲染的优先级表格无法识别 + 飞书激进虚拟滚动让需求 6/8/10 的具体内容拿不到**
2. 切到 playwright → 报错 `Browser is already in use for browser-mcp-profile`
3. PowerShell 排查 → 发现 7 个**残留 Chromium 进程**（playwright 历次启动失败但 Chromium 没退出）持有 lockfile
4. 杀掉残留 Chromium → 锁释放 → playwright 一次步进抓取（200px 步长 + 1.5s 停留 + 累积去重）拿到全部 10 条需求详情

**这一段直接验证了 skill 的"工具中立 + 失败优雅降级 + 显式告知用户"原则**——AI 没有偷偷换工具，每一步都按 skill 规则报告失败原因 + 让用户决定下一步。"chrome-devtools 不擅长长文档内容提取" 也被实证（SKILL 早就警告过）。但 **chrome-devtools 真正擅长的是测试回归**——见 §6.7 延伸。

### 6.4 项目地图让分析"立刻聚焦"

阶段一进 PROJECT-MAP，按 PRD 关键词命中：

| PRD 关键词 | 命中条目 | 直接给出的位置 |
|---|---|---|
| "中国制造网边栏" | mai/assistant（嵌入态） | `business/default/dashboard/chat/chat.store.js` |
| "智能拓客" | mai/astronaut · §速查表 | `pages/leadGenerator/`，path `/skill/leadGenerator` |
| "视频生成（麦可平台的）" | mai/astronaut · §1.3 | `pages/videoGenerate/`，path `/skill/videoCombiner` ⚠️ **path 与目录名不一致**（地图明示，否则容易迷路）|
| "社媒营销" | mai/astronaut · §速查表 | `pages/mediaMarketing/`，path `/console/mediaMarketing` |

没有这些条目的话，需要全仓 grep 多个关键词反复定位，token 消耗显著更高，且容易漏掉"path 与目录名不一致"这种关键坑。

### 6.5 实测产出

阶段一一次输出对所有 4 条需求覆盖：

| 输出维度 | 实际产出量 |
|---|---|
| 现状定位（具体到 `<file>:<line>`）| 12 处 |
| 改动点（具体 `<file>:<line>`）| 15+ 处 |
| 待确认问题（人工校验项）| 5 类 |
| 跨调用方 / 递归路径 / 反模式回归警告 | 3 处 |
| 复用建议（从深度地图速查表挑出现成方案）| 6 处 |

**所有 file:line 都通过 grep / Read 验证过，无一处编造**——SKILL 的"找不到就直说"硬约束让 AI 不会因"想给完整答案"而胡编位置。

### 6.6 时间对比（与同类需求基线对照）

| 子任务 | 之前裸 AI 协作 | toolkit + 项目地图 |

### 6.7 延伸：从需求分析到自动化回归

§6.5 中阶段一为需求 8 / 10 输出的"测试范围"全部是 **chrome-devtools 可执行的步骤**——同一份 SKILL 输入策略决策树（§4.5），把 chrome-devtools 的本职从"调试"扩展到"自动化回归"。

**需求 8（视频生成防重复提交）的回归用 chrome-devtools 跑通**：

- `navigate_page` → 视频生成页
- `fill_form` 填 5 项设置（视频/字幕/配音/背景音乐/数字人）→ `click` 提交 → `list_network_requests` 验证 `videoGenerate4DigitalHuman` 触发 1 次
- 不改设置 → 再次 `click` 提交 → `take_snapshot` 看 Modal 弹出 + 文案正确 → `list_network_requests` 验证接口**未触发**
- `click` "取消" / "继续生成" → 各自验证 XHR 行为

**需求 10（跨页勾选丢失）的回归用 chrome-devtools 跑通**：

- `navigate_page` → 社媒营销 → 打开产品列表弹窗
- `click` 第 1 页勾 2 个 → `click` 翻页到第 5 页 → `click` 勾 2 个 → `click` 提交
- `evaluate_script` 拦截 confirm 回调 / `list_network_requests` 抓提交接口请求体
- 验证传出的 prodId 数组 = 4 个完整产品

**为什么是 chrome-devtools 而不是 playwright**：

这两条需求的回归核心是 "**XHR 内容 + UI 状态 + 控制台报错**"——SKILL §4.5 表格明示这正是 chrome-devtools 的本职。**§6.3 chrome-devtools 在长文档读取上"不擅长"的另一面，就是它在测试回归上"称职"——SKILL 决策树把这两面同时讲清楚了**。

**这把 skill 从"分析助手"扩展为"PRD → 实现 → 验证"完整链路的骨架**：

| 阶段 | 工具 | 职责 |
|---|---|---|
| 抓 PRD（登录态）| playwright | 步进抓取 + 突破虚拟滚动 |
| 阶段一·需求理解 | 项目地图 + 复用查找规则 + 反模式条目 | 给 file:line + 改动量 + 测试范围 |
| 阶段四·实现 | （Claude 直接编辑） | - |
| 阶段五·review | （Claude 自查） | - |
| **阶段五延伸·回归** | **chrome-devtools** | **XHR / Snapshot / 控制台 自动验证** |
| 阶段六·维护 | 提案式 Edit | 沉淀经验进地图 |

工具中立 + 失败优雅降级的规则**复用**到了"输出验证"——一份决策表，覆盖 PRD 抓取到测试回归全程。

### 6.8 副产物：阶段六维护机制的现场触发

实战还产出几条可继续维护进地图的内容（**正是阶段六维护机制的设计意图**——靠工作流本身把维护契机暴露出来）：

1. **mai-astronaut.md §11 业务概念地图**可新增"视频生成-设置项分布"条目（5 个设置项：视频/字幕/配音/背景音乐/数字人 ↔ 5 个 components 文件一一对应）

3. **PRD 抓取的"步进 200px / 1.5s 停留累积去重"** 可作为登录态长文档的标准提取模式沉淀

## 七、它实际带来什么

### 7.1 单次需求的提效

设计阶段对照估算 + §六实战 1 次印证（mai-static，4 条 P1 需求阶段一）。设计估算与实测基本吻合（75% vs 80%），但仍需多人多场景扩展验证。

| 任务 | 之前（裸 AI 协作）| 之后（用 toolkit）|
|---|---|---|
| 接到 PRD → 输出摘要 + 风险 + 落点 | ~15 min | ~3 min |
| 复用判断（"有没有现成的？"）| ~5 min/次 | ~1 min |
| 接口联调 mock 数据（五态）| ~20 min | ~3 min |
| 提交前自查 | ~15 min | ~5 min |

单次需求综合：**~60 min → ~15 min**，提效 ≈ 75-80%。

### 7.2 结构性收益（更难量化但更重要）

- **跨项目零迁移**：换项目不用换 skill，只换项目地图（每个项目维护一份 .claude/toolkit/）
- **AI 输出的可信度上升**：复用建议必须 file:line、找不到就承认——AI 不再"自信地胡说"。§六实战中 27+ 处 file:line **无一处编造**
- **经验能持久化沉淀**：阶段六维护机制让"踩过的坑"有了归属位置，下次新对话直接读地图。§六中需求 10 直接命中预先记录的反模式条目，是这条收益的最直接演示
- **AI 协作不再依赖具体某个工具**：MCP 决策树让用户用什么读什么，工具中立。§六中 chrome-devtools 失败 → playwright 接住，过程对用户全透明

### 7.3 变化的本质

skill 不是把 AI 变得更聪明，而是**把 AI 协作的失误成本前置**。失误模式被约束到 prompt 层之后，每次对话不再赌"AI 这次会不会编"，工作流变成可预期的事——这种可预期性本身就是工程化价值。

## 八、约束与边界

### 适用范围

- 工作流相对稳定的工程化场景：前端项目交付、后端 API 开发、测试用例设计等
- 团队愿意一次性投入维护 `.claude/toolkit/` 项目知识层（投入 1-2 人天 / 项目，长期收益）
- 使用 Claude Code（其他 AI agent 通过 npx skills 也能装，但深度功能 Claude Code 适配最好）

### 不适用

- 没有相对稳定流程的探索性 / 一次性项目
- 单 prompt 能完成的小任务（用 toolkit 反而过度设计）
- 不愿维护项目知识层的团队——地图过期会让 skill 失效

### 风险与人工把关

skill 设计时把几个关键风险点直接写进了规则：

- **AI 产出的验证**：每个阶段都有强制人工确认点，特别是接口字段 / 错误码 / 鉴权 / 边界状态 / 业务规则——必须显式标"待人工校验"
- **数据安全**：skill 工作流不引入额外数据流转，所有读写仍在用户本地 CC 会话；项目知识层是 per-repo 文件，敏感项目可 .gitignore 排除；公开 SKILL.md 仅含工作流规则，不含任何项目敏感信息
- **不适用场景**：skill 顶部的"何时不使用"明确列出，不会被误用到无关场景
- **人工复核节点**：阶段五 review 是预审不是终审、阶段六维护要走"提案 → 确认"流程、阶段一/三的人工校验项明确——每个关键节点都标好了"由谁把关"

skill 自己写明：**AI review 是预检，不替代人工 review、测试和业务验收。**
